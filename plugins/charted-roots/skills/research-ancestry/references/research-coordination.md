# Coordination and the scale of overhead work

Apply this when resuming research, during parallel work that has already been agreed, or when cataloguing, checks and reporting start to take up a significant share of the research. For a single worker and a small question, the existing vault notes — `Search Plan -`, `Survey -`, `Hypothesis -` (`research.md`) — are enough. These recommendations do not authorise new delegation, publication or changes to infrastructure.

## Resuming and preserving the work

After a break, compare the current `Search Plan -` note, the question-relevant `Survey -` and `Hypothesis -` notes, the Sources and Citations they link, recent corrections (`git log` / `git diff` on the affected notes) and the user's latest decisions. An old summary or report does not substitute for the current notes; before asking again or searching again, check whether the answer has already been obtained (search the vault, the letters folder and the letters index for replies, and `History/`). When handing over, state how much history is available: full notes and git history, excerpts, or only a summary. Do not fill gaps with guesses and do not turn an agent's proposal into the owner's decision. If after a crash it remains unresolved how to apply a finding, record that state in the existing Search Plan together with the material, the reason and the next step. Work through the changes relevant to continuing under the vault's rules, while carrying on with other available checks.

When reporting a pass after resuming, show the new checks and results. If only a title or catalogue description was available, say so at once and give the established archival reference, if any. State separately which entries or pages were actually read, what was checked in them, and which questions remain open. Take the starting coverage from the Survey notes, and explain the grounds for any significant repeat of earlier work.

In a multi-branch task, choose the next checks by the user's goal, material contradictions, expected usefulness, accessibility and cost. Consider useful branches left aside long ago, and re-checking relationships already accepted, alongside extending the tree. Keep the queue and the resumption point in the Search Plan, without mandatory quotas of people, documents, task ratios or universal time thresholds. Record the applicable events and gaps in the existing notes for the question, without requiring every biographical field to be filled.

When rewriting a shared note, keep recovery possible: git is the safety net, so check the diff of the affected lines, wikilinks, `_id` values and unexpected deletions before moving on. Do not drop properties or sections you do not recognise. With Obsidian open and bidirectional sync on (`enableBidirectionalSync` + `syncOnFileModify`), write one side of a relationship only, keep scripted edits to small batches, and re-read a note before a follow-up edit — the plugin may have rewritten it (`CLAUDE.md` § Invariants). On a version conflict apply the reconciliation order below.

On a forced stop, save the result, the actual coverage and the next useful step in the Search Plan or Survey; an environment limit does not mean the sources are exhausted. Do not promise work after the reply unless a continuation mechanism has actually been started. A dispatched task does not prove the worker's activity or result; a drafted letter does not prove it was sent, and a prepared change does not confirm it is visible in the target service. Check the affected result within access already permitted, and leave an unverified application as awaiting confirmation.

## Several workers and a shared vault

- **Divide the writing.** State which branches, notes and files each worker changes. For shared notes (a Person, a Place, the letters index), agree on one worker who applies changes, or use git and the existing review. Uniqueness of identifiers: every `cr_id` is generated fresh, and filenames stay unique vault-wide (`CLAUDE.md` § Working conventions); do not impose a new ID scheme. For helper scripts and intermediate files changed concurrently, use separate working paths in the session scratchpad. A shared cache is acceptable with agreed query keys and writing without conflicting overwrites; one file per query does not by itself rule out a race between two workers.
- **Hand over results without writing files.** If a worker can only return text, hand over the material in compact chunks, each labelled with its coverage and a resume point. After a break-off, request only the missing part. Before applying to the vault, check which chunks have arrived and reconcile repeats and gaps in the usual order.
- **Review coverage in a long case.** If there are still grounds to suspect a missed route, compare the available catalogues and collections for the place, period and question with what has already been checked. Under an agreed division of work a separate worker may do this. Assess possible additions against the current Search Plan and actual coverage.
- **Reuse what has been found.** Before creating a new note or fetching material again, check existing Sources, transcriptions and scans by archival code, URL and `cr_id`. Reuse a suitable saved version; record new versions and provenance details separately (one Source per archival item, `archive.md`). A matching name does not authorise merging people. Record a presumed identity as a separate decision in a Hypothesis, under the rules of evidence.
- **Check immediately before acting.** If several workers could send the same request, assign the sending to one of them in the existing Search Plan. That worker checks the available state (the letters folder, the letters index, replies already received) just before the user sends it (`correspondence.md`, section 3). For a shared note, check the current version and the uniqueness of the affected `cr_id`s and filenames within the agreed order of writing or merging.
- **Hand over changes with their grounds.** For a handover it is enough to give the base commit, the affected notes (wikilinks / `cr_id`), links to the material, the proposed changes, contradictions, actual coverage and the next step. Do not attach the whole earlier archive to every package when stable links are available; state the necessary context and any material the recipient cannot access. Keep a full copy when an agreed snapshot or handover genuinely needs one.
- **Reconcile before applying.** Before applying, compare the package's base commit with the current state of the vault. A stale snapshot must not overwrite another branch's newer decisions; carry over the task-relevant changes, checking for conflicts. Distinguish a prepared change, a handed-over change, applied edits and a verified result (`verify-vault` over the changed notes). The message "task dispatched" or a patch file does not by itself confirm that the vault has been updated.
- **Keep the grounds when editing a biography.** Compare the edited passage with the available previous version (git) and the sources. For every statement kept, keep its source, known locator and any caveats that affect the meaning. Link the mentions kept to people already established. Carry disputed identities and dates over with their uncertainty. Shorten and correct the text within the agreed scope, observing the privacy rules (`privacy-and-safety.md`).

## Keeping processing proportionate to the task

- **Name the expected benefit.** Before a new index, graph or mass tagging, decide which agreed question it will help answer: finding mentions, checking a relationship, seeing coverage, or resuming after a pause. Start with a volume sufficient for that task and expand according to results. If the user commissioned a full review of an archive, keep that scope; do not replace it with a search for one surname.
- **Keep working methods.** Before a new one-off script or reprocessing, check existing tools (`scripts/familysearch.py`, `scripts/gwar.py`, `scripts/scan_montage.py`, the plugin's `lib/` scripts) and earlier results. Use a suitable proven path with new parameters; there is no need to build a universal platform first. When the format or input assumptions change, re-check the affected part.
- **Justify repeat passes.** Take into account that the material is unchanged and an earlier Survey exists when choosing the scope of a repeat check. A full check is justified, for example, after a transfer, on suspected damage, or by an agreed preservation plan; new arrivals need their own checks. Do not cancel existing preservation requirements, and do not take an earlier checksum as proof of a file's current state.
- **Measure the result when comparing approaches.** The number of notes, scripts, batches and passed technical checks does not establish reading quality or savings. If choosing between approaches, or justifying complexity by expected savings, compare on suitable tasks the information found, omissions, time to search or resume, and maintenance cost. Use available observations or a small targeted example; fulfilling a direct user request does not by itself require a separate measurement project. Without measurement, label presumed savings as a hypothesis.

## Extended scan reading

When sequential image viewing starts to bloat the context, split the chosen range into small parts by year, section or group of frames. Choose the size by legibility, the environment's capabilities and useful output; there is no universal frame threshold and no mandatory model.

- If delegation is available and permitted in the current environment, give the reader a specific range, the question, the name/place forms sought, the available images or permitted local copies, and the reading rules. Choose the worker by quality on these materials, not only by price. Without subagents, work in the same small batches in the tool at hand.
- Return compact text: frame/leaf and source ID → the entry found and its material columns, doubts, the range actually viewed and gaps. Links and coordinates let the main agent open the chosen line with its context. Do not take a brief handover for a full reading of every frame; check disputed spots per `field-lessons.md`, section "Checking a visual reading".
- **Keep the actual coverage current in the Survey note.** Find earlier passes by the file's stable archival reference and copy (search the Surveys and Sources); where copies differ, do not carry coverage over automatically. For the question, record the range, the purpose, the rectos or versos checked and the gaps, and what was merely obtained, viewed in overview, read substantively or left partial. Hand over the range and the resumption point; if an earlier entry overstated the reading, correct it (git keeps the history).
- An overview montage helps navigation but does not by itself confirm reading or exclusion: check material entries on individual legible frames with context. Repeat a previously clear stretch for a new question, a better image or a specific doubt, not mechanically.
- After a substantive batch, save in the Survey (coverage, findings, unresolved readings) and the Search Plan (resumption point, next useful stretch). Give the user brief progress reports during long work. If the size of the next stretch is known, state it approximately; do not promise tokens, cost or savings without measurement.
- Respect the budget and stopping point set by the user. When continuing the same question, carry over the accumulated spend and the state of the pass across changes of page, task ID, reply or worker. Restore the data relevant to the work from the latest notes, counting progress towards a source separately from new biographical facts. If an explicit limit is expected to be exceeded, save the result and agree an extension; an ordinary new batch within the scope already commissioned needs no confirmation. Access, payment and external transfer remain separate actions under the existing rules (web work, uploads and e-mail only on the user's explicit instruction).
